# Staging alerts and operational evidence

The repository includes tested alert rules and a private Prometheus/Alertmanager configuration. It does **not** install monitoring services, configure an owner's notification destination, or prove that a notification can reach anyone. Deploy this configuration on a private network after provisioning staging, then complete the receipt and recovery drill below before the pilot.

## Validate without hosting

Run `bash scripts/staging/check-alerts.sh` with the repository's Node tools and Docker available. It validates ten rules, their firing/resolution/metric-absence fixtures, the Prometheus scrape configuration and an inert Alertmanager receiver. Containers run with networking disabled, read-only filesystems, a temporary memory-backed test directory, no published ports and no persistent volumes. Image downloads may occur before those isolated validations; no application services or receiver are contacted.

The validation images are pinned by version **and** multi-platform manifest digest in the script: Prometheus 3.15.0 and Alertmanager 0.34.1. Upgrades require rerunning these fixtures. The examples follow the official [rule-testing contract](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/) and [Alertmanager routing configuration](https://prometheus.io/docs/alerting/latest/configuration/). These validation versions are not an assertion that an unreviewed monitoring deployment is secure or up to date.

## Private deployment

Use `ops/alerts/prometheus.example.yml` with `ops/alerts/flare.rules.yml`. Mount a fresh, deployment-specific `METRICS_TOKEN` at `/run/secrets/flare_metrics_token`; it must match Flare's API, worker and SMTP relay configuration. Do not put the token in source control or inline in the scrape config. The examples expect Compose service DNS names `flare-api:4000`, `flare-worker:4001`, `flare-smtp-relay:4002` and `alertmanager:9093` on the same private network. Update both scrape targets and the explicit `FlareTargetMissing` expectations when changing discovery. Never publish metrics, Prometheus or Alertmanager to the public Internet; administer through the reviewed SSH/private access path.

`ops/alerts/alertmanager.example.yml` intentionally has a receiver named `owner-not-configured` with no integrations. This is valid syntax but sends nothing. Copy it into private deployment configuration and replace that receiver with the owner's approved destination and file-mounted credentials. Assign a primary and backup human responder. Keep alert labels, dashboards and notifications free of addresses, message content, tokens and tenant identifiers.

The worker polls durable metrics every 15 seconds through its existing single non-overlapping lifecycle task. One read-only database statement has a 2.5-second statement timeout and 0.5-second lock timeout. Counts are capped at 10,001 per kind; that value means **at least 10,001**, not an exact total. Queries do not change delivery state, request work or redrive anything. Redis and object-store probes happen outside that transaction with a 2.5-second readiness deadline. Database/pool outages may prevent a sample from completing; the stale timestamp alert covers that independently.

| Exported metric                                  | Meaning and boundaries                                                                                                                                                                                                                                                                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flare_pending_operations{kind}`                 | Existing compatibility metric for all pending workflow/email/webhook operations, including future scheduling.                                                                                                                                                                                                                                     |
| `flare_due_operations{kind}`                     | Eligible workflow, email, webhook, inbound, forwarding, automation, publication, broadcast and event-outbox work. Future schedules/backoffs are excluded. Held email is counted separately.                                                                                                                                                       |
| `flare_oldest_due_operation_seconds{kind}`       | Age since the oldest currently eligible operation's due time; zero for an empty kind. Email uses the later of schedule/retry times. A later publication item cannot bypass an unfinished earlier item. It is an eligibility-age measure, not time since initial acceptance or a total outage duration.                                            |
| `flare_dead_letters{kind}`                       | Persisted terminal failures matching Flare's dead-letter view, including retry exhaustion, permanent failures, workflow ambiguity and failed cancellation. Counts do not mean every item is safe to redrive. Historical failures remain visible until their state changes through supported recovery.                                             |
| `flare_sending_safety_issues{kind}`              | Fixed categories: held messages, ambiguous email identities, ambiguous workflow runs, suspended organizations, stale DNS records and stale transport attestations. Email ambiguity counts each message once even with multiple attempts; persisted ambiguous attempts remain visible even when a subsequent callback updates a recipient outcome. |
| `flare_operational_collection_success`           | 1 after a complete validated database snapshot; 0 after a failed collection. A failure retains old counts rather than reporting healthy zeroes.                                                                                                                                                                                                   |
| `flare_operational_collection_timestamp_seconds` | Time of the last complete snapshot, zero until collection. Rules use the worker service's series; API/relay imports of the shared telemetry registry do not claim to run this collector.                                                                                                                                                          |
| `flare_dependency_ready{dependency}`             | Last worker probe for `database`, `redis` or `objects`. This covers shared dependencies, not every API, native Novu or Postal dependency.                                                                                                                                                                                                         |

Metric labels use fixed enums plus existing service/target labels. No organization, domain, recipient, operation ID, transport instance or provider response is a label. Staleness counts are deliberately narrow: existing unrevoked Production transport attestations or verified Production sending domains checked more than 24 hours ago (or dated in the future). Development, disabled senders and revoked attestations are excluded. **Zero stale records does not establish sending readiness**: missing evidence, DNS drift, alignment and transport bindings still require the domain/operator APIs and genuine receiver evidence.

## Respond to alerts

| Alert                                       | Initial response                                                                                                                                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `FlareTargetDown` / `FlareTargetMissing`    | Restore service availability or the reviewed private scrape/token configuration. Check `/ready` and service logs. A missing target is not healthy.                                                                         |
| `FlareOperationalMetricsStale`              | Restore the collector's database access or investigate timeouts. Until the next successful snapshot, retained gauges are old evidence.                                                                                     |
| `FlareDependencyUnavailable`                | Restore the indicated shared database, Redis or object-store dependency; verify recovery before resuming the pilot.                                                                                                        |
| `FlareDurableBacklogOld`                    | Work has been eligible for more than five minutes continuously for another five minutes. Inspect its queue, leases, provider state and policy; do not blindly replay sends.                                                |
| `FlareDeadLettersPresent`                   | Inspect the tenant dead-letter view and attempts. Use audited recovery only for supported eligible records. Existing known terminal history can keep this warning active; do not erase history just to clear an alert.     |
| `FlareAmbiguousAcceptance`                  | Preserve operation identity and collect provider/receiver evidence. Never automatically retry or fail over an uncertain send. A callback can resolve a recipient without resolving all ambiguity on the logical operation. |
| `FlareSendingHeld` / `FlareSenderSuspended` | Review policy holds, quota/route bindings and authenticated feedback. Suspension requires a recent-MFA operator and an audited reason to resume. Keep feedback ingestion running.                                          |
| `FlareSenderEvidenceStale`                  | Refresh genuine receiver/DNS evidence through the normal operator flow. Do not fabricate attestations or bypass readiness.                                                                                                 |

Safety/backlog/dead-letter rules require a fresh successful database collection, so old counts cannot masquerade as current findings. Collection failure has its own critical alert. Thresholds are conservative staging defaults, not mailbox-provider standards or an availability SLO. Preserve evidence and tune thresholds only after measuring the pilot.

A cold backup intentionally stops services. Before approved maintenance, create an explicit, bounded Alertmanager silence with the owner, reason, ticket and expected end time. Verify the silence expires and services/scrapes recover afterward. The backup command must not automatically suppress or dismiss monitoring. Do not globally inhibit ambiguity or sender-suspension alerts as a shortcut to a quiet dashboard.

## Required external monitoring gates

The application exports neither host filesystem usage nor off-host backup success. These are **pending deployment gates**, not silently passing alerts:

- Install and restrict an appropriate host exporter (for example, Prometheus node exporter), confirm the data volume/mount labels and alert on both free bytes and free inodes. Test the rule with the real volume layout; monitoring only `/` may miss a dedicated data disk.
- Monitor an independently verified successful **encrypted off-host** backup/upload receipt and a separately recorded restore rehearsal. A local archive's creation time, log line or remote object's existence alone does not prove recoverability. Agree the receipt schema and maximum age with the backup operator before creating a metric; no synthetic `flare_backup_*` success series is supplied here.
- Use an off-host availability/watchdog check. A Prometheus process running on the same failed host cannot notify on its own absence.
- Add private checks for native Novu/Postal readiness and expected public HTTPS/DNS from outside the host. The Flare worker dependency gauge does not cover these systems.

## Live notification and recovery drill

1. Record the deployed rule/image revision, chosen private receiver, responder and expected maximum delivery delay. Ensure the default discard receiver has been replaced.
2. With the owner's approval, inject one clearly labeled synthetic test alert into the private Alertmanager and then resolve it. Verify actual firing **and resolved** notification receipt at the selected destination; capture redacted timestamps/receipt evidence. A successful API response or rule test is insufficient.
3. In a controlled window, interrupt one private scrape/dependency. Confirm the intended alert fires, the responder can locate the runbook, the service recovers and the alert resolves without duplicate sends. Confirm missing/stale metrics are visible.
4. Exercise a bounded maintenance silence, expiry and notification recovery. Test the off-host watchdog and host/backup exporters independently.
5. Save redacted evidence with the staging acceptance record. Until this is complete, report **rules locally validated; live alert delivery unverified**.
