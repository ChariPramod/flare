## Zod 3 compatibility backport

[GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) reports allocation of per-element validation failures before checking collection size. The [upstream Zod 4 fix](https://github.com/colinhacks/zod/commit/a0ebf97) rejects oversized constrained collections before walking their contents. Flare uses Zod 3 schemas and its OpenAPI converter; replacing the API with Zod 4 during a release freeze would change validation contracts.

The narrowly registered [Zod 3 patch](../../patches/zod@3.25.76.patch) backports early upper-bound rejection for arrays (`max` and exact `length`) and sets (`max`/`size`) in source, ESM and CommonJS. Existing successful values and error codes/messages remain compatible; oversized arrays now return the size error without collecting every child error or executing refinements. Regression tests cover 100,000 invalid entries, nested paths, async validation, exact lengths and valid boundary transformations through both entrypoints.

The npm audit service still reports the unchanged **3.25.76** package version. This is a documented local backport, not an audit-clean upstream release. It does not impose a new limit on unconstrained arrays or maps. Keep maximum sizes on untrusted collections, retain HTTP byte limits and rate limiting, and review new schemas for bounded processing. A future Zod 4 migration must revalidate generated OpenAPI, error shapes and all consumers before removing the patch.
