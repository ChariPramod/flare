# Staging pilot: email, Inbox and password/MFA

No staging host, domain or DNS zone has been provisioned. These files prepare a provider-neutral single-host deployment; they do not deploy resources or certify external delivery. The initial pilot uses self-hosted Postal, email and Inbox, with password login and MFA. OIDC, SES, SMS, push and chat remain separate future checks.

The owner resumed staging preparation on 2026-10-14; hosting budget, region, domain and access details are still pending. The earlier infrastructure baseline, `82ec8c9`, passed all five jobs in [CI 38613630116](https://github.com/ChariPramod/flare/actions/runs/38613630116), including isolated Caddy routing/header checks. Resume provisioning only after those infrastructure decisions and access are available.

## Provisioning checklist

- Choose a dedicated host with a stable public IPv4 address, permitted outbound TCP 25 and control of its reverse-DNS/PTR record. Confirm these capabilities with the hosting provider before purchase; a generic VM does not imply mail egress is allowed. An initial planning allocation is 8 vCPU, 16 GiB RAM and 150 GiB SSD on Ubuntu 24.04 amd64, matching CI's OS family. This allocation has not been capacity benchmarked.
- Obtain a staging domain or delegated DNS zone controlled by the operator. Use a dedicated sender/receiving domain and explicitly controlled recipient mailboxes; keep the pilot separate from production traffic and customer lists.
- Provide a non-root SSH operator with sudo and Docker access, recovery access, an owner email, an ACME contact email, a private secret store and an encrypted off-host backup destination. Docker access is equivalent to administrative host access. Install Docker Engine/Compose v2, Node 22, pnpm 10.32.1 and OpenSSL.
- Record the approved hosting region and budget, owned DNS zone and operator access, host address, SSH username and local key-file path, backup destination, and the named person responsible for secret custody and recovery. Supply credentials through the secret store or private local files, never in repository documentation. Provisioning remains pending until these deployment inputs are available.
- Allow public TCP 80/443 and optionally UDP 443 for Caddy. Allow inbound TCP 25 only when testing Postal receiving, using the explicit override below. Do not publish databases, Redis, MinIO, Postal administration, native Novu administration or Flare's authenticated SMTP submission port.
- Check that `172.30.250.0/24` does not overlap host/VPN routes. The template reserves `.10` for Caddy and `.11` for the web service; dynamic containers are allocated only from `172.30.250.128/25`, preventing startup-order collisions with those trusted addresses. Changing this subnet requires reviewing the overlay, both static IPs, allocation pool, trusted proxy addresses and preflight together.

## Hostnames and routing

Replace the examples in `ops/staging/env.example` and merge its settings into the deployment checkout's private `.env`; do not append duplicate keys. Keep one canonical `.env` for Compose interpolation and service `env_file` values. Preserve internal endpoints such as `postgres`, `minio`, `novu-api` and `postal`; these are not public origins.

| Setting                  | Purpose                                                        |
| ------------------------ | -------------------------------------------------------------- |
| `STAGING_DASHBOARD_HOST` | Dashboard and its authenticated `/api` and `/novu` proxies     |
| `STAGING_API_HOST`       | Flare `/v1/*` API and signed `/t/*` tracking routes            |
| `STAGING_WS_HOST`        | Only native Inbox `/socket.io` paths                           |
| `STAGING_TRACKING_HOST`  | Sender-domain tracking alias, normally `track.<sender-domain>` |
| `STAGING_ACME_EMAIL`     | Certificate operations contact                                 |

Point dashboard, API and websocket A records to the host. Add AAAA only if IPv6 ingress is configured and reachable. Set the tracking hostname's CNAME to the API hostname, matching the record returned by Domains. Keep `TRACKING_URL=https://<API hostname>` as the CNAME target; actual MIME tracking links use the sender domain's tracking hostname. The Caddy configuration obtains certificates for both names. If additional sender domains need tracking, explicitly add their names to the ingress configuration and certificate plan before enabling tracking.

For Postal, set A and PTR consistently for `POSTAL_HOSTNAME`, publish the receiving MX records and the exact SPF, DKIM and return-path records generated by Postal and Flare. Authorize the sender domain in Postal as well as in Flare. Configure `POSTAL_SPF_HOST`, `POSTAL_RETURN_PATH` and the `dns`/`postal.smtp_hostname` sections of private `ops/postal/config/postal.yml`; preflight checks SMTP hostname, MX, SPF and return-path consistency and rejects their generated localhost settings. Postal's `web_hostname` may remain specific to the private administrative tunnel. If using Postal route-address routing, also replace `dns.route_domain` and configure its DNS; this optional route-address setting is not checked by preflight. Keep `postal.allowed_request_destinations: [flare-api]`. Use [provider setup](email-pipeline.md#provider-setup) and [signed inbound routing](inbound.md), including Postal RawMessage/BodyAsJSON submission to the verified domain's callback. Real inbound requires the optional port-25 override and DNS route to Postal.

Postal's raw API cannot promise mandatory TLS to final recipient servers. Use the default `enforce_tls=false` for this explicitly opportunistic-TLS pilot; a domain requiring mandatory final-hop TLS needs a transport that actually supports that guarantee. Do not set a capability flag merely to bypass this restriction.

## Secrets and internal relay trust

Create fresh staging secrets with the existing setup procedure in a separate checkout; never reuse acceptance/development credentials or overwrite an existing deployment's `.env`. Then replace development hostnames, owner settings and certificates. Keep `.env`, the relay private key, Postal signing key and Postal configuration mode `0600`; secret directories should be `0700`. Keep the relay key owned by the numeric `FLARE_UID` configured for its service.

Use a private CA to issue the internal relay server certificate with a **DNS SAN for `flare-smtp-relay`**, server-auth usage and a matching private key. Put the leaf plus any intermediates in `ops/certs/relay.crt`, its private key in `ops/certs/relay.key`, and the trusted CA bundle in `ops/certs/relay-ca.pem`. The staging overlay mounts the CA bundle into Novu and sets `NODE_EXTRA_CA_CERTS`. Public ACME certificates cannot normally cover this internal service name; the development self-signed localhost certificate is rejected. Never copy the private CA signing key into the deployment containers.

Leave public ingress stopped during first-time bootstrap. Postal's existing port 5000 and other administrative ports remain bound to `127.0.0.1`; they are reachable only from the host or an explicitly authorized tunnel. Use the same base/staging Compose file set throughout:

1. After configuring secrets, hostnames and the relay CA, start private Postal/Novu dependencies:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d --build --wait postal novu-api novu-worker novu-ws
   ```

2. Initialize the Postal organization/server and native Novu owner/organization using private administration over SSH. Set the provider bootstrap credentials and `NOVU_DEVELOPMENT_API_KEY` / `NOVU_PRODUCTION_API_KEY` in private `.env`, each from its proper provider/environment. Configure `MAIL_TRANSPORTS` with named instance IDs and private environment references for real sending; the legacy `POSTAL_API_KEY` alone is insufficient. Keep `MAIL_SANDBOX=false` and follow the [sender reputation guide](sender-reputation.md) for route isolation, callbacks and per-instance public keys. Configure Postal sender authorization and signed callbacks. Keep the global `NOVU_APPLICATION_IDENTIFIER` empty: each Novu environment has its own identifier and must be configured separately in Settings after owner login.
3. Start the private Flare services and explicitly create the owner and tenant environments. **Migrations alone do not create an owner account.** The identity seed uses the configured `SEED_OWNER_EMAIL`, `SEED_OWNER_PASSWORD` and `SEED_API_KEY`:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d --build --wait flare-api flare-web flare-worker flare-smtp-relay
   docker compose -f docker-compose.yml -f docker-compose.staging.yml exec -T flare-api node packages/db/dist/seed.js
   ```

4. Record the intended operator user UUID in `FLARE_OPERATOR_USER_IDS` and recreate the API with that environment. The allowlist is separate from tenant ownership. Run the offline preflight and ingress validation below, then start ingress. Log in at the configured HTTPS dashboard origin, enroll MFA, and configure each environment's own Novu application identifier and confirm its API key in Settings. Never use a raw HTTP tunnel origin for browser mutation requests while `WEB_ORIGIN` remains the HTTPS dashboard; a pre-ingress browser session requires a secure tunnel and matching hostname/origin routing.
5. Optionally set `SEED_SUBSCRIBER_EMAIL` to a mailbox you control and `SEED_DOMAIN` to the dedicated pilot domain, recreate the API service to load changed environment values, then create the sample domain/subscriber/Inbox workflow:

   ```sh
   docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d --no-deps --wait flare-api
   docker compose -f docker-compose.yml -f docker-compose.staging.yml exec -T flare-api node packages/mail/dist/seed.js
   ```

Both seeds preserve existing organization/domain data; rerunning the identity seed does not update an existing owner's password or Novu settings. Sample seeding is optional and does not send email. Publish and verify the returned DNS records before any controlled pilot send. Application-level credentials and environment mappings require live smoke tests; offline preflight cannot certify values already stored in the database.

## Offline preflight and deployment

Run from the deployment checkout after installing dependencies:

```sh
node scripts/staging/preflight.mjs
# Or inspect another prepared checkout without changing it:
node scripts/staging/preflight.mjs --root /srv/flare-staging
```

Preflight performs no DNS requests, network calls, Docker commands or cloud operations. It reports only fixed issue codes and configuration field names, never values. It rejects sandbox mode, missing named transports and empty/invalid operator UUID allowlists. It validates strict named transport configuration and referenced private values without exposing them, and checks public origins, independent secrets, private file modes, duplicate/interpolated env entries, provider configuration, relay SAN/key/date/CA trust using local OpenSSL, Postal key correspondence (including every named transport referencing the bundled `postal` host), callback allowlisting, database-password consistency, and the SMTP/MX/SPF/return-path configuration described above. Blank provider credentials or generated SMTP/sender-domain localhost settings fail until bootstrap is completed. OpenSSL/LibreSSL chain validation and Node's explicit SAN check work on both the Mac and Linux. The report always lists outstanding external checks, including the live operator identity/MFA session, organization approval, route binding, physical pool isolation and fresh sender readiness; a clean result is configuration evidence only. Preflight cannot certify that an allowlisted UUID exists or has MFA enabled. Establish those gates in `/operator` before any real pilot send, using the [sender reputation operating guide](sender-reputation.md).

For CI or a Docker-equipped developer host, `bash scripts/staging/check-config.sh` validates both merged Compose variants and the pinned Caddy configuration using disposable synthetic settings. Configuration validation uses `--network none`. A second runtime check starts Caddy and synthetic Node upstreams on an internal Docker network, with no published ports, deployment secrets or persistent volumes. It verifies private-route denial, upstream routing and rejection of spoofed client-IP headers using HTTP fixture origins; it cannot issue public certificates or launch Flare application services. Actual HTTPS issuance, distinct-client rate limiting and host reboot recovery remain deployment checks. The ordinary unit suite also tests the preflight against a generated private-CA chain and rejected configurations. See [testing](testing.md) for the remaining service/browser acceptance commands.

Validate the merged model without printing expanded credentials:

```sh
docker compose -f docker-compose.yml -f docker-compose.staging.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.staging.yml run --rm --no-deps ingress caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
docker compose -f docker-compose.yml -f docker-compose.staging.yml up -d --build --wait
```

The overlay uses ordinary Compose merges, with no `!override` extension. Existing loopback ports stay loopback; adding the overlay does not remove them. The native Novu API/dashboard and all database services have no public ingress routes. Caddy responds 404 for `/internal` and `/v1/internal`, including descendants, and health/metrics routes. Its administration API is disabled. Caddy overwrites `X-Flare-Client-IP` on requests sent to the dashboard; the web service forwards a validated IP only when `FLARE_FORWARD_CLIENT_IP=true`. Flare trusts exactly the Caddy and web addresses. Do not expose the web/API loopback ports via a second proxy that bypasses this boundary, or trust an entire private/public subnet.

The staging overlay gives PostgreSQL, both Redis services, MinIO, MariaDB and MongoDB `restart: unless-stopped`, matching the application daemons. A host or Docker daemon restart therefore restarts the durable dependencies as well; explicitly stopped containers remain stopped. Initialization and migration jobs remain one-shot. Restart policies do not enforce Compose health-based startup ordering during daemon recovery: verify service readiness after a reboot, and use the same Compose `up -d --wait` command to reconcile unhealthy services before resuming the pilot. Include a controlled host reboot and readiness check in staging acceptance; configuration validation alone does not prove reboot recovery.

Only after receiving is configured and authorized, include the additional file on every subsequent Compose command for that deployment:

```sh
docker compose -f docker-compose.yml -f docker-compose.staging.yml -f ops/staging/postal-inbound.yml up -d --build --wait
```

That file publishes native Postal SMTP on TCP 25. It does not publish Flare SMTP AUTH on 2525. Configure host/provider firewalls independently. Keep the chosen Compose file set in the deployment runbook; using a different set later changes the desired services and port bindings.

## Pilot acceptance and recovery

Confirm public DNS and certificates from outside the host, HTTP-to-HTTPS redirects, authenticated password/MFA login, browser Inbox delivery/read state, and 404 responses for public internal/native administration routes. Verify the client-IP limiter with distinct clients and spoofed forwarding headers. Then create/verify the real domain, submit to controlled recipients, inspect delivered MIME/DKIM and provider delivery callbacks, test suppression/preferences, and receive a signed Postal RawMessage. Confirm that provider acceptance and final delivery remain distinct. Record DNS/provider evidence separately from local/CI simulations.

Public smoke checks should expect `/ready`, `/health` and `/internal/metrics` to return 404. Run dependency-readiness checks on the host's loopback API or through an authorized SSH tunnel; do not weaken ingress to make a public health probe pass. The Python staging checks' `--staging-internal` mode is reserved for that loopback/tunnel endpoint, while ordinary staging mode checks the public boundary. Enroll the pilot owner in MFA and store recovery codes with the designated custodian before additional accounts join.

Back up the complete stores and secrets using [deployment recovery](deployment.md#backup-and-restore), including Caddy's persistent certificate volumes, and complete an isolated restore using the off-host backup before opening the pilot more broadly. Preserve records of ambiguous sends; never replay them automatically after restoration. No production availability, mail reputation, recovery objective or external acceptance is claimed by this template.
