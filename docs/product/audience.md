# Audience, templates and broadcasts

Contacts, typed properties, segments, audience topics, templates and broadcasts belong to one organization/environment. Composite foreign keys and forced tenant policies prevent cross-environment references. Suppression remains organization-wide. Audience contacts are separate from Novu subscribers; audience topics are distinct from notification fan-out topics.

## Contacts and preferences

`/v1/contacts` supports upsert, paged search and segment/list filtering. Contact detail supports updates, soft deletion, topic preferences and signed preference-link creation. `/v1/contact-properties` defines string, number, boolean or date properties with validated fallbacks. Define properties before importing values. Segment rules support all/any matching, equality, inequality, containment, numeric comparison and existence; values are bound SQL parameters.

In **Contacts → Import contacts**, choose CSV, tab-separated TSV, JSON or Excel `.xlsx`. Select an Excel worksheet, map columns, review validation errors and choose a named list before importing. Email is required; other columns can map to `first_name`, `last_name`, `unsubscribed` or `properties.NAME`, or be ignored. JSON accepts an array of objects and flattens nested `properties` into mappable columns. The file and unfinished mapping stay in memory while the session is active, never in browser storage. Nothing is imported until you confirm.

Preview/import accepts at most **2 MiB per file, 5,000 rows, 100 columns and 4,000 characters per cell**. Excel additionally allows at most 20 worksheets, 100,000 populated cells and 16 MiB expanded archive content. Formulas, external references, macros and unsafe workbook structures are rejected; export values only when necessary. Older binary `.xls` files must be saved as `.xlsx` or CSV first.

Imports validate and commit atomically: an invalid row prevents all writes. Case-insensitive duplicate addresses use the last row's mapped fields while preserving any opt-out. Existing opt-outs cannot be reset by import, previously deleted contacts are skipped, and names whose columns were not mapped remain unchanged. Imported/created/updated/duplicate/deleted counts explain the result. Importing a file does not prove permission to email its contacts.

Named lists preserve imported cohorts and appear in `/v1/contact-lists`; filter contacts with `?list_id=...`. A contact can belong to several lists without being duplicated. Reusing a list name adds to the existing list in the current environment; it does not replace its membership. For a distinct campaign cohort, use a distinct name. Imports may also add to a selected existing list or omit a list. Lists and their references use composite tenant keys and forced row policies.

The API accepts `POST /v1/contacts/import/preview` with `{source, mapping?}` and `POST /v1/contacts/import` with `{source, mapping, list_name?}` or `list_id`. `source` is `{format, data, sheet?}`: UTF-8 text for CSV/TSV/JSON and base64 bytes for XLSX. Preview with mapping returns row errors and existing-contact/duplicate counts; import validates again within its transaction. Legacy `{csv, mapping}` import and `{csv}` preview requests remain supported. Import bodies, previews and results are omitted from request logs.

Preference links are signed bearer capabilities, scoped to one contact and environment, and expire after one year. Anyone with a link can change that contact's broadcast preferences; do not distribute them outside the recipient's email. Request logs redact the token. The public page requires no dashboard session. Global opt-out overrides topic defaults and explicit topic choices. Opt-out does not remove organizational bounce/complaint suppressions, or change transactional notification preferences.

Broadcast MIME includes List-Unsubscribe and List-Unsubscribe-Post, with both fields covered by DKIM. The one-click endpoint accepts URL-encoded or multipart `List-Unsubscribe=One-Click` POST bodies without cookies; GET does not unsubscribe. Production requires HTTPS PUBLIC_API_URL and WEB_ORIGIN, following [RFC 8058](https://www.rfc-editor.org/rfc/rfc8058.html). The local demo may use loopback HTTP only with `MAIL_SANDBOX=true`, a validated Mailpit-only configuration and sandbox dispatch adapters. Public HTTP and real transports remain blocked. Mailbox-provider interoperability still needs live validation.

## Versioned templates

`/v1/templates` creates a named identifier; `/v1/templates/:id/versions` appends immutable subject/HTML/plain-text/variable-fallback content. Editing is limited to Development. Select a version for preview or direct email submission with `template: { id, version, variables }`. Omitting version pins the current version during submission. Idempotency hashes the original validated request before resolving templates, so a replay retains its original message even after the template changes.

The renderer supports scalar `{{variable}}` and nested `{{payload.name}}` lookups with HTML escaping. It does not execute JavaScript, helpers, partials or arbitrary React components. Broadcast HTML must contain `{{{FLARE_UNSUBSCRIBE_URL}}}`; the generated URL is still escaped. The dashboard preview blocks scripts and remote assets.

Workflow email control values may reference `templateId` and optional `templateVersion`. Flare copies that version's subject and HTML into the saved workflow; Novu performs subscriber/payload interpolation at execution. Template fallback variables are for Flare email rendering, not injected into Novu. Re-save a workflow to select changed content. Publication copies pinned template dependencies with workflows and automations; see [publication](publication.md). Templates are not a separate selection category in the dashboard publication dialog.

## Broadcast delivery

In **Broadcasts → Create campaign**, name the campaign, choose all contacts, a named list or a segment, and optionally select an audience topic. After an import, **Create campaign for this list** preselects the imported cohort. Enter a verified sender and either compose subject/HTML/plain text in Development or choose an immutable saved-template version. Include `{{{FLARE_UNSUBSCRIBE_URL}}}` in HTML; the composer starts with an unsubscribe link. Production uses published templates. Saving a draft does not send anything.

On the campaign page, review total and eligible recipients, a small eligible-recipient sample, and exclusions for global opt-out, suppression, topic preferences or deletion. Edit a draft, preview its email, then **Send now** or **Schedule for later** and confirm. Local schedule input uses your browser's timezone, displayed before confirmation, and is converted to an ISO instant. Cancel a scheduled/running campaign to stop remaining work. Counts are a current preview; eligibility is checked again before delivery.

Create/edit drafts at `/v1/broadcasts`, pinning a template version or campaign-owned inline content, sender, optional `list_id` or `segment_id`, optional topic and rate of 1–50 messages per second. Inline edits append campaign-owned template versions without changing shared templates. `GET /v1/broadcasts/:id/audience-preview` reports eligibility; non-draft campaigns use their frozen membership. Optional `Idempotency-Key` on draft creation returns the same campaign after a retry and rejects a different payload with HTTP 409. Keys are scoped to the organization/environment and retained with the campaign. The dashboard retains a creation key across a failed response.

Scheduling accepts the shared ISO/timezone or natural-language schedule format, rejects zero-eligible audiences, requires a verified sending domain and honors immutable API-key domain scope. Audience membership is frozen atomically at scheduling; rescheduling a not-yet-started campaign rebuilds the snapshot. Later imports do not silently enlarge a scheduled campaign. Lists and segments cannot both be selected, and a missing or foreign selector is rejected rather than interpreted as all contacts. Sender approval, marketing route approval and quota limits still apply to delivery.

Workers claim a broadcast in PostgreSQL and process at most one rate-sized chunk per second. Each recipient's message and campaign progress commit together. PostgreSQL is authoritative; queue entries can be reconstructed after Redis loss. Preferences, deleted contacts, topic opt-outs and organization-wide suppressions are checked at submission and again before delivery. Property fallbacks fill absent/null values.

Canceling prevents future audience submissions and cancels queued messages that have not started delivery. An active transport request may finish. Broadcast status `sent` means audience submission finished, not that every email was delivered. The detail screen separately reports skipped/failed audience entries, message states and unique human engagement. Provider acceptance and confirmed delivery retain their separate meanings.

Broadcast/contact lifecycle events use the transactional outbox and existing webhook delivery system. A processing error rolls back the chunk and backs off one minute. Per-recipient validation errors are recorded without stopping valid recipients. Journaled attachments/MIME objects left by rolled-back transactions are eligible for guarded orphan cleanup. Active or committed references and legacy untracked objects are retained; see [retention and cleanup](../operations/reliability.md).

## Verification

Local database tests cover atomic CSV import, opt-out preservation, numeric/fallback segments, template immutability, original-request idempotency, frozen audiences, DKIM unsubscribe headers, preference rechecks, throttling/cancellation and tenant/domain scope. Browser coverage uses the real dashboard with an explicit test API fixture. Real PostgreSQL/Redis/MinIO recovery and local SMTP scenarios have passed in Docker; current revision-specific evidence is in [the acceptance ledger](../development/acceptance.md) and [progress](../../PROGRESS.md). External mailbox-provider interoperability remains a staging gate.

## Broadcast recovery boundary

The dispatcher holds the original organization-policy and broadcast locks through batch rollback and durable failure/backoff recording. An unexpected batch failure rolls back its message, recipient and outbox changes before recording a retry deadline. Another worker cannot advance between that rollback and backoff. Recipient-level policy pauses preserve earlier accepted recipients and leave the blocked recipient pending. Pacing and retry deadlines use current database time after processing, so lock waits and slow work do not shorten them.

A lost connection or failed commit is recovered from committed state; the worker never opens a separate delayed failure transaction that can overwrite a newer batch or cancellation. Cancellation retains the same policy-before-broadcast lock order. Existing provider acceptance and ambiguous-message safeguards remain in the shared mail pipeline; a broadcast marked submitted is not evidence of final recipient delivery.
