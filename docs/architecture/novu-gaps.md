# Novu community compatibility

Pinned target: API, worker, WS and internal dashboard 3.19.0. Never downgrade below 3.18.0.

Verified against the [v3.19.0 Compose source](https://github.com/novuhq/novu/blob/v3.19.0/docker/community/docker-compose.yml): the upstream example itself still pins 3.18.0. Flare overrides these tags explicitly. The pinned runtime images now execute in CI and on the Apple Silicon development Mac. Novu runs natively on ARM64; Postal 3.3.7 uses AMD64 emulation. Candidate-specific results and external verification limits are recorded in [the acceptance ledger](../development/acceptance.md).

Team limits, topics, layouts, translations and webhook availability require live community-image tests. Flare does not assume cloud-only features are available. Do not present untested edition behavior as a runtime finding.

Flare owns team authorization, org/environment isolation, API key scoping, suppression, idempotency, email transport retries/failover, workflow dispatch recovery, email tracking and signed webhooks. Channel failure normally continues execution; delay, digest and throttle failures cancel remaining steps. HTTP request failures halt by default and support an explicit `continueOnFailure: true` control. Provider acceptance must never be labeled delivery.

Reference: [Novu releases](https://github.com/novuhq/novu/releases/tag/v3.19.0), [Postal container processes](https://docs.postalserver.io/other/containers/).

## Flare implementations

Topics and subscription conditions are stored and expanded in Flare before trigger dispatch. This supplies exact context matching and actor exclusion independently of community topics availability. Flare promotes selected workflows, layouts and translations through durable publication operations with pinned dependencies and engine reconciliation. Novu transport acceptance is labeled `accepted`, not delivered. Native job execution is verified for the bounded action matrix below; production callback/timeline integration still needs provider evidence.

Flare now adopts only the current environment’s Inbox singleton and uses the native email/SMS primary endpoint. A provider being configured is not evidence of notification delivery.

[CI run 38442762577](https://github.com/ChariPramod/flare/actions/runs/38442762577) subsequently passed the entire pinned-stack acceptance script, including translated email relay delivery, preference updates, verified content publication, Production automation execution and all five real browser flows. [CI run 38538818077](https://github.com/ChariPramod/flare/actions/runs/38538818077) on `7d91b54` also passed native Inbox delivery/subscriber isolation/read-state persistence, the actual dashboard Inbox, and the delay/digest/throttle/HTTP assertions described below. All six live browser flows passed.

`scripts/acceptance/actions.mjs` supplies the passing runtime assertions for the action row. It creates workflows through Flare and reads the pinned engine's notification/job API. The isolated HTTP listener is reachable only inside the disposable Compose network, with a per-run random route and a 4 KiB request limit. The acceptance override permits precisely `flare-api` alongside the existing relay hostname; production SSRF configuration is unchanged.

The action checks require a two-second delay before downstream execution, two concurrent events merged into one digest with both payloads retained, one winner among four concurrent throttle attempts, skipped throttle children, and renewed execution after the native reservation expires. HTTP checks require rendered JSON, the native signature header, persisted failure plus canceled children, and explicit continuation with the failure retained. This does not certify cron schedules, dynamic throttles, HTTP signature verification by an external receiver, arbitrary third-party endpoints, or action recovery after loss of Novu's own Redis data.

The pinned engine's [Redis throttle implementation](https://github.com/novuhq/novu/blob/v3.19.0/libs/application-generic/src/services/throttle/redis-throttle.service.ts) adds a default 30-second reservation buffer to the configured window. A one-minute throttle therefore retains its reservation for 90 seconds; a trigger at 61 seconds remains skipped, as observed in [CI run 38534097037](https://github.com/ChariPramod/flare/actions/runs/38534097037). The acceptance test reads back the native one-minute controls and submits a fresh trigger after 91 seconds. It does not shorten or disable the buffer. This is an engine timing limitation, not a guarantee that throttled work will automatically resume: skipped triggers remain terminal.

Flare emits HTML explicitly for its email editor and precompiled templates/layouts. Native block content remains available only when explicitly selected in API control values. Workflow preference requests use complete `all` and `channels` objects; Novu returns the default layer as `preferences.default`. Subscriber preference updates instead use boolean channel values. SDK contract tests and publication reconciliation tests cover these distinctions; runtime acceptance is tracked separately in [the evidence ledger](../development/acceptance.md).

## Retry ownership and failure semantics

The hosting-independent `engine-restart.mjs`/`.sh` scenario passed in [CI 38619037497](https://github.com/ChariPramod/flare/actions/runs/38619037497) on `6b841e2`. It stops the native worker after two delayed Inbox jobs have persisted, cancels one through Flare, restarts native Redis without deleting its AOF volume, and requires one surviving notification and no canceled delivery. It also checks original notification IDs, one Flare dispatch and no duplicate after a second worker restart. That checkpoint tested graceful restart; the later abrupt-crash and complete native queue-loss evidence is recorded below. The subsequent API-outage phase passed on `1a743b5` in [CI 38619875142](https://github.com/ChariPramod/flare/actions/runs/38619875142): local activity remained available while the native API was stopped, and the delayed survivor resumed once after restoration.

Flare retries definitively rejected workflow submissions and recovers its own queued work. Once Novu accepts a trigger, downstream SMS, push, chat and action execution belongs to Novu; Flare does not provide generic provider failover for those channels. Email accepted by the Flare relay enters the shared durable email pipeline and its configured transport priority.

Pinned-source inspection confirms that [delay, digest and throttle failures halt the chain](https://github.com/novuhq/novu/blob/v3.19.0/apps/worker/src/app/shared/utils/should-halt-on-step-failure.ts), using the engine's [action classifier](https://github.com/novuhq/novu/blob/v3.19.0/libs/application-generic/src/utils/digest.ts); legacy `shouldStopOnFail` can also halt a channel. [HTTP request execution](https://github.com/novuhq/novu/blob/v3.19.0/apps/worker/src/app/workflow/usecases/send-message/execute-http-request-step.usecase.ts) returns its own halt decision according to `continueOnFailure`. The [worker records failed sends and applies that continuation decision](https://github.com/novuhq/novu/blob/v3.19.0/apps/worker/src/app/workflow/usecases/run-job/run-job.usecase.ts). These source findings do not certify runtime timing or credentialed channel delivery. Ambiguous Flare submissions remain quarantined, regardless of provider retry capabilities.

## Native job inspection and destructive acceptance

Activity now reports observed native job states and check/update timestamps separately from Flare dispatch status. A reachable engine with no matching notification is `not_found`; unavailable details and bounded incomplete results remain explicit. A shared five-second deadline covers at most ten notifications and fifty jobs per notification. Cancellation is offered for locally queued work or complete observations of pending delay/digest work, uses the parent trigger and warns that concurrent or already-sent work cannot be recalled. Observations never resubmit accepted work.

The expanded `engine-restart.sh` kills the native worker with SIGKILL and requires exit 137 before canceling one delay while it is stopped. Redis AOF remains intact; the surviving Inbox notification must arrive once after restart. This tests a native worker killed while waiting on persisted delayed work, not a Flare dispatcher killed during an uncertain provider request.

The separate `crash-recovery.sh` scenario stops every native Redis producer, deletes only DB2 in the disposable native Redis, retains Mongo and Flare Redis, and observes accepted delay/digest work beyond both deadlines. Its assertions require retained pending job evidence, no Inbox delivery, one logical operation/attempt, rejected redrive and successful explicit cancellation. These assertions passed in CI `38627811798` on `ef54d28` and again in CI `38629040758` on `e178006`. This is characterization of lost queues, not an automatic recovery mechanism.

For an actual native queue-loss incident, pause new triggers, preserve Mongo/Redis evidence and backups, and inspect transaction IDs, job timestamps and downstream effects. A pending Mongo record alone cannot tell whether its Redis job exists. Restore native queue data only under the deployment recovery procedure and reconcile provider/Inbox effects before deciding on replacement work. Do not redrive accepted/ambiguous operations or create replacement triggers solely because they look old. Flare's automatic recovery of its own durable queued work does not reconstruct destroyed native queues. Explicit cancellation closes pending work; it cannot undo external side effects.

The additional `dispatch-crash.sh` scenario targets Flare's own uncertainty window. An internal acceptance-only proxy forwards one real trigger and withholds the response; the runner requires SIGKILL before Flare records acceptance or timeout. It waits for the unchanged one-minute lease and requires one ambiguous attempt/outbox event, one native Inbox delivery, a stable transaction/notification identity and rejected redrive across a second restart. No production fault hooks or database lease mutations are used. It passed in [CI 38629040758](https://github.com/ChariPramod/flare/actions/runs/38629040758) on `e178006`, including the actual one-minute lease expiry and a 30-second observation after the second restart. See the acceptance ledger for the full evidence boundary.

Use `workflow reconcile --before <ISO timestamp>` to collect bounded, metadata-only observations for accepted work, or `workflow inspect <run-id>` for one run. Observation age, incomplete results and cancellation eligibility are explicit. Neither command proves Redis queue presence or replays/cancels work. See the [CLI guide](../../apps/cli/README.md) for limits and continuation cursors.
