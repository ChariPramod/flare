# Acceptance and evidence

Run `bash scripts/integration.sh` for real PostgreSQL/Redis/MinIO/Mailpit tests and `bash scripts/acceptance.sh` for the pinned full stack. Both scripts require a local Linux Docker engine with Compose, Node 22 and pnpm 10.32.1. The read-only `scripts/local-docker.mjs` prerequisite refuses remote SSH/TCP Docker targets before registering cleanup or starting containers. Integration uses a unique project and exact disposable loopback database/Redis URLs; occupied ports fail startup without resetting existing stores. Install Playwright Chromium with `pnpm exec playwright install chromium`. On this Mac, the installed Chrome can be selected with `E2E_BROWSER_CHANNEL=chrome`. Full acceptance needs the loopback ports in Compose to be free and enough memory/disk for Flare, Novu, MongoDB, PostgreSQL, Postal/MariaDB, Redis, and source-built MinIO. No external provider credentials are required for the local simulation.

The full-stack script copies source into a new private temporary directory, generates independent credentials/certificates, starts an isolated Compose project, and removes its containers, volumes and files on exit. It never uses the existing checkout's `.env`, certificates or data volumes. Disposable browser origins are pinned to `127.0.0.1`, matching Compose's IPv4 port bindings; the launcher rejects conflicting `E2E_BASE_URL` overrides before launching with fixture credentials. Ordinary `test:e2e:live` runs retain their explicit deployment URL support. It applies current migrations and separately upgrades a disposable database from the committed `62aaa57` migrations, checking existing workflow content survives. It seeds twice, configures the pinned Novu owner/environments through its real API, and creates Flare integrations. Generated private files, browser traces and raw provider logs are not uploaded as CI artifacts. On failure, only bounded, filtered error lines with credentials and opaque values redacted are printed.

A private authoritative CoreDNS zone publishes the actual generated DKIM/SPF/MX records. Flare's normal verification poller resolves them through `DOMAIN_DNS_SERVERS`; no test marks domains verified directly. This certifies resolver/parsing/polling behavior against local DNS, not public DNS propagation, provider ownership or email deliverability. The override accepts only operator-configured resolver IPs and must never derive from an API request.

The scenarios exercise real Flare HTTP authentication, real Novu workflow acceptance, locale fallback, pinned content publication/reconciliation, preferences, Novu → SMTP AUTH/STARTTLS → Flare → Mailpit, Bcc hiding, DKIM source, suppression and inbound persistence/retrieval. Postal-shaped inbound callbacks are signed using a locally generated RSA key; those are simulated submissions. Delivery events injected by the test are explicitly tagged `acceptance-simulated-delivery`, not represented as real provider confirmations. Browser tests cover login/workflow, domain/email, inbound sandbox/source download, layout publication and safe dead-letter redrive.

Additional hosting-independent scenarios run after authentication and email setup. `oidc.mjs` starts a local HTTPS issuer and separate Flare API process using the generated localhost certificate; it exercises real discovery, JWKS signatures, state/nonce/PKCE, claims, replay, invitation gating and MFA. Only this isolated child trusts the test CA and fixed test proxy address; production TLS checks stay enabled. `postal-native.mjs`/`.rb` use the pinned Postal runtime's MessageDB, RawMessage serializer, SHA-256 signer, HTTP destination guard and webhook delivery service. They store synthetic messages without queueing SMTP and test native callback persistence, deduplication and rejection. These scenarios passed in CI on `abaa551`. The outcome data remains synthetic: they do not establish external issuer interoperability, public Postal routing or actual recipient delivery.

The load stage stops the worker, submits at the default 10 requests/second plus a simultaneous 40-request burst, checks throttling headers and repeated idempotency keys, then deletes only the disposable Redis database and restarts the worker. It requires all accepted logical messages to reach Mailpit with exactly one transport attempt and no duplicate database operation. API/worker RSS is sampled against a configurable `ACCEPTANCE_MEMORY_MAX_BYTES` ceiling (768 MiB default). This is a bounded reproducible smoke load, not a maximum throughput benchmark or production sizing guarantee.

The sustained mixed-load stage defaults to 180 seconds, with `ACCEPTANCE_SOAK_SECONDS=600` selecting a ten-minute local run. It continues fresh email, signed inbound and native Inbox work through a controlled 20-second Flare worker pause, verifies actual Mailpit receipt counts alongside logical identities/outbox/Inbox contents, and bounds request latency, sampled process RSS and oldest durable backlog. This stage uses sandbox quotas; the existing separate policy integration tests verify pilot admission limits. Results below distinguish the actual duration and host from the existence of the scenario.

The populated upgrade stage now snapshots the committed baseline before migrating, restores that actual `pg_dump` into a second isolated database, and upgrades it again. Both paths run migrations twice. The final multi-store restore additionally proves rollback-only tenant writes and broader behavioral isolation; neither rehearsal enables delivery or substitutes for off-host recovery. See [testing instructions](testing.md#sustained-load-and-populated-upgrade-rehearsals) and [upgrade boundaries](deployment.md#populated-upgrade-and-snapshot-fallback-acceptance).
